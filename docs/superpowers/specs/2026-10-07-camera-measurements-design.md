# Studio camera performance collection

This increment implements the remaining measurement preparation for M4.4 in the accepted [product design](2026-10-06-open-source-product-design.md). Run the actual Studio camera, solver and Three.js preview through an optional diagnostic sink. A separate development HTML entry mounts Studio with the sink and local download controls. The normal production entry has no diagnostic controls, timers, collection or source-code payloads. Keep Native inline execution and one fresh final review.

## Required behavior

- Camera and MediaPipe remain default denied. Opening the tool, declaring conditions, or starting diagnostics must not start a camera/model. The operator separately grants the existing session SDK permission and clicks Start camera. Require a ready camera, a working preview, an unpaused live-preview workflow, explicit local actor permission and complete declared device/source metadata before starting collection.
- Capture the real successful pose/hand delegates, SDK/model pins and delivered camera dimensions/frame-rate hint. Preserve Fast's existing pose model, alternate-frame hand cadence, 150ms hand reuse, crop, calibration, recording and consent behavior. Never store device IDs, pairing codes, image pixels, landmarks, motion frames, or source video in a timing receipt.
- Each distinct video input attempted by the existing loop records source time, detection start, callback finish, pose/handler/detector status, hand state and first actual 3D render-call completion for its solved frame. Repeated renders do not inflate FPS; solved frames replaced before rendering remain explicitly unrendered. Observer failures must end diagnostics without stopping ordinary capture or changing motion output.
- Freeze declared metadata and capture context at collection start. Settings, camera generation, calibration, workflow, Live Link or mirroring changes, camera/model/preview failures, page hiding, and permission withdrawal end a bounded partial receipt. Permission withdrawal stops diagnostics synchronously as well as preserving existing capture cleanup.
- Limits: 180000ms collection wall interval, 21601 attempts, 32MiB compact JSON, 32 interaction observations. Invalid/nonmonotonic clocks or dimensions end an incomplete receipt. A stalled camera still reaches the private tool's wall timeout. Resources/timers/subscriptions/blob URLs belong to the tool and are released on unmount. Prior downloadable results survive an invalid new-start request.
- The receipt schema is `emotecap-camera-measurement-v1`, always `qualification: pending`. Record operator-declared full lowercase source commit, synthetic/observed classification, laptop/desktop model/OS/CPU/GPU/browser, warmup, actual context/setup, SDK/model pins and exact SHA256 of the four instrumented source files. Declarations and digests are traceability, not release/hardware authentication.
- For a completed valid interval, exclude attempts started before `startedMs+warmupMs`; divide distinct successful rendered attempts by the entire remaining wall interval to get effective rendered FPS. Also report attempt FPS, failed-pose/handler/detector fraction, unrendered successful count, nearest-rank p95 detection-to-render-call latency and optional next-animation-frame interaction p95. No successful render gives zero effective FPS and null render latency; zero attempts gives null failure rate. Exhausted warmup or incomplete receipts have no summary. Failed attempts and final trailing idle time stay in the denominator.
- Latency begins immediately before crop/detection and ends after the existing Three.js render call returns. It excludes sensor exposure, frame arrival before the loop, GPU completion and physical screen presentation. Interaction timing ends in the next animation-frame callback. Name these boundaries explicitly; neither is a physical camera-to-screen or perceived-response claim.
- A Fast720p candidate label requires Fast, no crop, delivered1280x720, a laptop declaration, observed classification and known delegates. It is still pending and has no automatic PASS, threshold or supported-device claim. Baseline thresholds await the specified actual laptop. This camera schema is distinct from the accepted video-import packet; no invented file SHA/pretend Python video comparison.

## Verification and exclusions

Use hand-computed timing/status fixtures for arithmetic, matching/replaced/mutated frame references, frozen metadata, clock/budget changes and failed observer isolation. Real Edge workflows must run actual Studio hook/solver/Three.js/receipt download with only owned synthetic camera and SDK controls; verify default denial, grant-only no processing, local rights, known Fast delegates/dimensions, no-pose/detector/hand failure, settings/withdrawal cancellation, cleanup and a readable narrow layout. Mark all such receipts synthetic and pending. Re-run existing camera/SDK flows and default production sample flow. Actual SDK inference/network, physical camera, operator-authorized actors, designated laptop, Unity/two rigs, clean-machine/new-user and publication gates remain pending. Preserve previous scratch and minor findings; do not push or publish this increment.
