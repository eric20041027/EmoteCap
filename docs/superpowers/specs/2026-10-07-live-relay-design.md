# M3 controlled local Live Link

This is the remaining M3 relay subsystem of the accepted M1–M5 product design. Native means inline execution followed by one fresh whole-plan review. The continuous execution authorization covers local implementation; public push, release and real user/hardware qualification remain separate gates.

## User behavior

Live Link is off by default. Turning it on explicitly creates a local pairing session and opens the source socket. Studio shows a copyable pairing code, connection state, expiry and errors without starting a camera, loading a model or saving credentials in a project. Unity uses the code in its Live Link component. A socket becoming open is not a successful protocol handshake. Stop closes the browser connection and requests session revocation; failed revocation is visible and the code expires automatically.

The supported relay is loopback on the same computer. Browser sources require a trusted loopback Origin; native Unity sinks can omit Origin but require the pairing secret. Browser Origin/Host checks complement secrets and do not claim to protect against malicious software already running as the user. No remote LAN pairing or cloud relay is introduced.

## Session and wire contract

- `POST /api/live-sessions`, no request body, trusted Origin/Host, creates `{id, sourceToken, pairingCode, expiresAt}`. UUIDv4 identity and independent 256-bit source/sink secrets are generated by the service. `pairingCode` is `<uuid>.<43-character base64url sink secret>`.
- At most four sessions exist; each expires after 3600 seconds of monotonic lifetime even when connected. Admission prunes expired sessions. Secrets live only in process memory and disappear on service restart.
- `DELETE /api/live-sessions/{id}` requires the source secret in `Authorization: Bearer ...` and trusted Origin/Host, invalidates immediately and closes only that session's sockets. Missing/expired session is404, wrong secret403, capacity409. Successful revocation is204.
- Socket URL remains `/ws/live?role=source|sink`, with no credential in URL. First text message within five seconds is `{type:'hello', version:2, bones:<exact canonical driven names>, sessionId:<uuid>, token:<role secret>}`. Strict integer version, exact role, identity, fields and bone order are required. No frame is accepted before this.
- Server hello acknowledgement is `{type:'hello', version:2, bones, sessionId, role, streamId, expiresAt}`. `streamId` is a new UUIDv4 for each source connection, or null for a sink waiting for a source. It contains no credential. A source reconnect resets the stream and sends a new hello to every paired sink before its next frame.
- One source at a time per session and at most four sinks per session. Separate sessions never receive each other's messages. A second source receives1008 and never displaces or mixes with the owner. Reconnect after a disconnected owner may reuse its unexpired source secret.
- Text messages are at most16KiB UTF-8. Binary, malformed JSON, extra fields, invalid version/bones, frames before hello, wrong credentials and sink transmissions after hello are rejected with1008 and bounded constant reasons; secrets/input are never logged.
- Frames have exactly `type,t,h,r`; strict finite numeric values (no bool/string coercion), `t>=0` strictly increasing per source connection with no180-second uptime cap, exactly3 hips values,192 quaternion values, `abs(h.x/z)<=1e-6`, quaternion norm in[0.98,1.02]. Accepted frame text is forwarded unchanged. No `clip_ready` support is implied.

## Slow receiver and ownership

Each sink has one pending latest frame and a separate pending hello/control state. A new frame replaces an unsent frame; control cannot be dropped by a frame. Source processing never awaits a sink network send. A sink worker has a0.5-second send deadline and is disconnected on failed/stalled send. Healthy receivers keep receiving. Queue storage is bounded by four sessions times four sinks times one16KiB frame plus bounded hello state. Sink/source registration and removal are exception-safe; expiry, explicit revocation and lifespan shutdown stop owned workers/sockets without touching unrelated resources.

The Web sender also drops frames above64KiB buffered data, validates poses before sending and uses a monotonic connection-relative live timestamp independent of take playback resets. It reconnects after ordinary closure at2000ms, waits at most5000ms for hello acknowledgement and stops automatic retry for policy rejection or expired pairing. Generation checks ignore stale socket/fetch callbacks after Stop/restart. Session creation/revocation use bounded local HTTP with5000ms deadlines and64KiB response limits. If a delayed session creation resolves after Stop, revoke its returned identity; an unconfirmed creation/revocation remains bounded by server capacity/expiry and a visible error.

## File boundaries and qualification

`server/emotecap_server/live/` owns protocol validation, session identities/admission, API/origin checks and relay lifecycle. The existing `relay.py` remains the import surface for `LiveRelay`; `main.py` installs routes and closes the relay at shutdown. `web/src/live/` owns the bounded client and pairing UI. No motion solver, project schema, export worker, credentials or provider configuration change is needed.

This plan delivers a testable service/browser contract. Updating and actually compiling the Unity receiver belongs to the immediately following Unity quality plan, where its fragmented-message bound, handshake, cancellation and two rig playback are tested using the real editor. The old unpaired Unity receiver is explicitly incompatible during this increment; M3 cannot be reported complete until that consumer is updated. Python/TypeScript protocol and actual Edge tests do not establish Unity, physical camera or latency/FPS qualification.
