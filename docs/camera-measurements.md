# Measure Studio camera performance locally

This private development tool runs the existing Studio camera, motion solver and Three.js preview. It prepares M4's specified-laptop baseline; it does not declare a supported device or completed release. Video import measurements use the separate [video tool](video-measurements.md).

## Run

1. Use the [frozen source development setup](development.md), then start the Web development server with `npm run dev` from `web/`. Open `http://localhost:5173/camera-measurements.html`. The default production build does not include this entry.
2. Enter the clean source checkout's full lowercase `git rev-parse HEAD`, device kind/model, OS/CPU/GPU/browser, classification and warmup. These are operator declarations. For an actual run choose Observed execution only when no camera/SDK substitutes are installed; controls remain Synthetic. Confirm local actor-processing permission.
3. In the Studio below, separately review/grant the session MediaPipe choice and click Start camera. Granting a choice or starting measurement does not start camera/models. For the target baseline choose Fast, no portrait crop and the agreed skeleton/smoothing. Finish any calibration before measurement. A selected camera's delivered resolution can differ from its requested resolution; the receipt records the actual size. Open samples/review/import pause camera tracking and cannot start a comparable run.
4. Click Start measurement. Let the camera/preview run through the agreed motion and warmup; use Measure next-frame response for an optional UI response observation. Click Stop measurement, then Download camera receipt. Use Stop camera or withdraw SDK permission when finished. Stop measurement leaves ordinary capture running.
5. Preserve each raw JSON with its run ID, actual machine/source evidence and agreed test procedure. Conditions are frozen at start. Changing capture/calibration/workflow/Live Link/mirror, delivered size/frame-rate settings, losing camera/models/preview, withdrawing permission or hiding the tab ends an incomplete receipt. Previous receipts remain available when a new request cannot start. Actual WebGL context loss ends diagnostics while body capture continues; after the context is restored and a render succeeds, start a fresh run.

The UI exposes actual Studio controls and can measure an already-started recording, but starting/stopping recording during a run changes its workflow and ends that run. Set up the workflow before starting; retain separate live-preview and recording runs. SDK permission withdrawal keeps the existing recording preservation/cleanup behavior.

## Receipt and arithmetic

`emotecap-camera-measurement-v1` is always `qualification: pending`. Current collection records declared metadata and five exact SHA256 source digests: App, usePose, PreviewCanvas, cameraMeasurements and videoFrameLoop. It also records SDK/model pins, successful pose/hand delegates, delivered camera dimensions/frame-rate hint, capture context, all attempts and up to32 interaction observations. Camera IDs, pairing codes, images, landmarks, motion frames and source video are absent. Source hashes identify instrumentation text; they do not authenticate the entire application, actor, hardware or an operator-declared commit.

Each attempt contains source time, presented-input counter or null, detection start/callback completion, status/hand state and the first render-call completion of its solved frame. Repeated renders do not count again; frames superseded before rendering remain unrendered. Current capture uses the video's native `requestVideoFrameCallback` when both request and cancel APIs are available. `inputFrame` is a valid nonnegative safe-integer `metadata.presentedFrames`; receipts explicitly identify `inputFrameDefinition: video-frame-callback-presented-frames`. It counts submitted video frames, not sensor exposures or distinct image contents. Equal native IDs are skipped. A strictly advancing valid ID can accompany an equal media-clock reading; a backward media clock or counter reset still ends an incomplete measurement.

Without both native APIs, capture falls back to animation-frame scheduling and changed media time, with `inputFrame: null`. It does not manufacture identity from time or output count. Missing identity withholds effective camera FPS and first-input latency; ordinary output/response observations remain available.

Earlier receipts used `totalVideoFrames-droppedVideoFrames` and four source digests. They remain unchanged and retain their original method/source scope. An observed Windows offscreen-video control showed that old counter stalling while source pixels and native IDs advanced; it does not establish the exact cause of the returned Mac B anomaly. See [counter correction evidence](superpowers/reports/2026-10-10-camera-counter-integrity.md). Do not relabel historical receipts as native-counter measurements.

Completed valid runs exclude attempts started before `startedMs+warmupMs`. The denominator is `finishedMs-startedMs-warmupMs`, including failed processing and trailing idle time. Effective rendered FPS counts the first successfully rendered attempt per presented-input identity over that entire interval. Output FPS counts all distinct solved-frame renders, and attempt FPS counts all detection attempts; these can exceed input FPS. Failure rate includes no-pose, no-frame, handler and detector failures among measured attempts. Successful but unrendered attempts are reported separately. p95 uses sorted durations at `ceil(.95*N)-1`, with first-per-input latency separate from all-output latency. No successes yield zero effective FPS with known input identity and null latency; no attempts yield null failure rate.

Latency starts immediately before crop/detection and ends when the actual Three.js render call returns. It excludes sensor exposure, pre-loop frame arrival, GPU completion and physical screen presentation. Response timing ends in the next animation-frame callback after the button event; it is a scheduling proxy, not perceived response. No FPS/latency threshold is inferred from synthetic controls or another machine.

The summary's `inputCounterProgress` describes attempts after warmup: `unavailable` if any identity is missing; otherwise `insufficient` with fewer than two attempts, `stalled` when their IDs never change, or `advancing` when IDs change. The UI explains that the first three states cannot establish fresh-camera throughput. Raw counters, calculated values, outputs and response observations remain intact even when a candidate label is withheld.

An observed laptop with Fast/no crop/delivered1280x720/known delegates and input identity may carry a pending Fast720p candidate label only with an `advancing` counter and at least one rendered output. There is no automatic PASS, supported-device declaration or replacement for the designated laptop baseline. A completed run with exhausted warmup, invalid clocks or changed conditions has no comparable summary. Partial receipts preserve observed errors. Fixed-source physical Mac B2, subjective foreground operation, final thresholds and the support matrix remain release gates.

Limits are180000ms wall time,21601 attempts,32MiB compact JSON and32 optional response observations. A private wall timer also stops a stalled camera; hiding/unmounting releases timers/subscriptions/Blob URLs and stops owned capture. Receipt data remain in memory until explicit local download and are not uploaded or stored in projects/IndexedDB. A refresh discards receipts. [Current actual SDK workflow](superpowers/reports/2026-10-10-current-frame-sdk.md) and earlier physical Mac/Unity observations retain their bounded scopes. Complete physical quality, current target-laptop measurements, clean-machine/five-user acceptance and redistribution/release gates remain pending in [release progress](release-progress.md).
