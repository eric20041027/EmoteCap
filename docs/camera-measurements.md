# Measure Studio camera performance locally

This private development tool runs the existing Studio camera, motion solver and Three.js preview. It prepares M4's specified-laptop baseline; it does not declare a supported device or completed release. Video import measurements use the separate [video tool](video-measurements.md).

## Run

1. Use the [frozen source development setup](development.md), then start the Web development server with `npm run dev` from `web/`. Open `http://localhost:5173/camera-measurements.html`. The default production build does not include this entry.
2. Enter the clean source checkout's full lowercase `git rev-parse HEAD`, device kind/model, OS/CPU/GPU/browser, classification and warmup. These are operator declarations. For an actual run choose Observed execution only when no camera/SDK substitutes are installed; controls remain Synthetic. Confirm local actor-processing permission.
3. In the Studio below, separately review/grant the session MediaPipe choice and click Start camera. Granting a choice or starting measurement does not start camera/models. For the target baseline choose Fast, no portrait crop and the agreed skeleton/smoothing. Finish any calibration before measurement. A selected camera's delivered resolution can differ from its requested resolution; the receipt records the actual size. Open samples/review/import pause camera tracking and cannot start a comparable run.
4. Click Start measurement. Let the camera/preview run through the agreed motion and warmup; use Measure next-frame response for an optional UI response observation. Click Stop measurement, then Download camera receipt. Use Stop camera or withdraw SDK permission when finished. Stop measurement leaves ordinary capture running.
5. Preserve each raw JSON with its run ID, actual machine/source evidence and agreed test procedure. Conditions are frozen at start. Changing capture/calibration/workflow/Live Link/mirror, delivered size/frame-rate settings, losing camera/models/preview, withdrawing permission or hiding the tab ends an incomplete receipt. Previous receipts remain available when a new request cannot start. Actual WebGL context loss ends diagnostics while body capture continues; after the context is restored and a render succeeds, start a fresh run.

The UI exposes actual Studio controls and can measure an already-started recording, but starting/stopping recording during a run changes its workflow and ends that run. Set up the workflow before starting; retain separate live-preview and recording runs. SDK permission withdrawal keeps the existing recording preservation/cleanup behavior.

## Receipt and arithmetic

`emotecap-camera-measurement-v1` is always `qualification: pending`. It records declared metadata, exact SHA256 of App/usePose/PreviewCanvas/cameraMeasurements source text, SDK/model pins, successful pose/hand delegates, delivered camera dimensions/frame-rate hint, capture context, all attempts and up to32 interaction observations. Camera IDs, pairing codes, images, landmarks, motion frames and source video are absent. Source hashes identify instrumentation text; they do not authenticate the entire application, actor, hardware or an operator-declared commit.

Each attempt contains source time, presented-input counter or null, detection start/callback completion, status/hand state and the first render-call completion of its solved frame. Old repeated renders do not count again; frames superseded before rendering remain unrendered. All detection calls stay visible, including multiple calls for one camera input. `inputFrame` is the browser's `totalVideoFrames-droppedVideoFrames`, a presented-video counter ([API](https://developer.mozilla.org/en-US/docs/Web/API/HTMLVideoElement/getVideoPlaybackQuality), [counter definition/reset](https://developer.mozilla.org/en-US/docs/Web/API/VideoPlaybackQuality/totalVideoFrames)). It is not an exposure counter or an image digest. A counter reset ends an incomplete run; unavailable identity withholds effective camera FPS and first-input latency rather than replacing them with output-call FPS.

Completed valid runs exclude attempts started before `startedMs+warmupMs`. The denominator is `finishedMs-startedMs-warmupMs`, including failed processing and trailing idle time. Effective rendered FPS counts the first successfully rendered attempt per presented-input identity over that entire interval. Output FPS counts all distinct solved-frame renders, and attempt FPS counts all detection attempts; these can exceed input FPS. Failure rate includes no-pose, no-frame, handler and detector failures among measured attempts. Successful but unrendered attempts are reported separately. p95 uses sorted durations at `ceil(.95*N)-1`, with first-per-input latency separate from all-output latency. No successes yield zero effective FPS with known input identity and null latency; no attempts yield null failure rate.

Latency starts immediately before crop/detection and ends when the actual Three.js render call returns. It excludes sensor exposure, pre-loop frame arrival, GPU completion and physical screen presentation. Response timing ends in the next animation-frame callback after the button event; it is a scheduling proxy, not perceived response. No FPS/latency threshold is inferred from synthetic controls or another machine.

An observed laptop with Fast/no crop/delivered1280x720/known delegates and input identity may carry a pending Fast720p candidate label. There is no automatic PASS, supported-device declaration or replacement for the designated laptop baseline. A completed run with exhausted warmup, invalid clocks or changed conditions has no comparable summary. Partial receipts preserve observed errors.

Limits are180000ms wall time,21601 attempts,32MiB compact JSON and32 optional response observations. A private wall timer also stops a stalled camera; hiding/unmounting releases timers/subscriptions/Blob URLs and stops owned capture. Receipt data remain in memory until explicit local download and are not uploaded or stored in projects/IndexedDB. A refresh discards receipts. Actual SDK network behavior, physical camera, authorized actors, target laptop, Unity/two rigs and human release gates remain pending in [release progress](release-progress.md).
